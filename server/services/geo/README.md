# Geo-Services

`postcodeService.ts` löst PLZ in DE/AT/CH zu Ortsmittelpunkten auf und hält Ergebnisse 30 Tage im Nitro-Cache. `roadDistanceService.ts` liefert Autofahrstrecken in Metern für einen Ausgangspunkt und bis zu 40 Ziele. Es nutzt die FOSSGIS/OSRM-Routenmatrix, hält erfolgreiche Werte sieben Tage und nicht verbundene Ziele 15 Minuten im Nitro-Cache. Lehnt OSRM eine Matrix wegen eines Ziels ab, werden die Ziele geteilt, bis erreichbare Ziele eigene Ergebnisse erhalten. Ein vorübergehend ausgefallener Provider wird pro Prozess 60 Sekunden geschont; die API nennt diese Wartezeit, damit der Client betroffene Ziele höchstens zweimal automatisch erneut abfragt. Koordinaten werden für Cache-Schlüssel auf drei Nachkommastellen gerundet. Anfragen an den Dienst sind innerhalb eines Serverprozesses auf höchstens eine pro 1,1 Sekunden begrenzt; bei mehr als acht wartenden Matrizen wird die zusätzliche Anfrage ohne Ersatzschätzung verworfen. `ROUTING_SERVICE_BASE_URL` kann serverseitig auf einen eigenen OSRM-kompatiblen Dienst zeigen.

`championshipLocationService.ts` besitzt bekannte Stadtmittelpunkte der derzeit angekündigten europäischen Regionals/Specials und weltweiten ICs. Neue Ortsnamen aus dem offiziellen Feed werden nur bei einem Cache-Miss über Nominatim aufgelöst, höchstens viermal pro Minute, und ein Jahr gespeichert; erfolglose Auflösungen einen Monat. Der Server sendet dabei nur öffentliche Stadtnamen, keine Nutzerposition. `CHAMPIONSHIP_GEOCODER_URL` kann serverseitig einen anderen Nominatim-kompatiblen Dienst wählen. Die Fahrstrecke zu Meisterschaften ist eine Näherung **zum Stadtzentrum**, da der offizielle Listenfeed nur Stadt und Land liefert.

`reverseLocationService.ts` löst eine freiwillig gespeicherte Geräteposition zum Ortsnamen auf. Der öffentliche GET-Vertrag `/api/locations/reverse?latitude=…&longitude=…` validiert und rundet beide Koordinaten auf drei Nachkommastellen und liefert `{ place, country }`. Der Server fragt Nominatim mit Stadt-/Ortsdetail ab; `nominatimRequestService.ts` begrenzt zusammen mit den Meisterschaftsabfragen alle Upstream-Anfragen pro Prozess auf mindestens 1,1 Sekunden Abstand (geplante Meisterschaftsabfragen mindestens 15 Sekunden) und acht wartende Anfragen. Ortsnamen bleiben 30 Tage, erfolglose Auflösungen 15 Minuten im Nitro-Cache. `DEVICE_REVERSE_GEOCODER_URL` erlaubt einen serverseitig konfigurierten Ersatzdienst. Die gerundeten Koordinaten gehen zur Ortsauflösung an den Dienst; die Oberfläche weist darauf hin und zeigt OpenStreetMap-Attribution. Keine Positionsdaten werden geloggt. Nachweis: `tests/unit/reverseLocationService.test.ts`.

Öffentliche Verträge: `/api/geo/postcode` für PLZ; `POST /api/events/road-distances` nimmt `{ origin: { latitude, longitude }, destinations: [{ latitude, longitude }] }` an und liefert `{ meters: (number | null)[], retryAfterSeconds: number }` in derselben Reihenfolge. `retryAfterSeconds` ist bei erreichbarem Provider null Sekunden; zusätzliche Antwortfelder sind für bestehende Verbraucher kompatibel. Die Route validiert alle Koordinaten und begrenzt Ziele auf 40. Es gibt keine Benutzeridentität oder Tenantdaten in diesen Requests; eingegebene Koordinaten werden an den Routingdienst übermittelt. Keine Koordinaten werden geloggt. Frontend-Darstellungen zeigen FOSSGIS/OSRM und OpenStreetMap-Attribution. In getrennten Deployments braucht der Geo-Dienst gemeinsamen Cache und eine verteilte Ratenbegrenzung oder einen eigenen Routingdienst. Verifikation: `tests/unit/postcodeService.test.ts`, `tests/unit/roadDistanceService.test.ts`, `tests/unit/championshipLocationService.test.ts`.
